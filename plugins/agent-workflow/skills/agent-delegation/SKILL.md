# Раздача работы агентам

Навык написан для Claude Code (инструменты Agent, SendMessage, Workflow, AskUserQuestion). Цифры и выводы выросли из порта сборки
DeceasedCraft на NeoForge 1.21.1 и проекта Space Journey (октябрь 2026); они подписаны там, где это важно. Метод от проекта не зависит.

Модель для агента выбирается по двум вопросам: есть ли у задачи готовый путь и что будет, если агент ошибётся. Важность задачи
тут ни при чём. Если путь задан (скрипт, спецификация, список вопросов), Sonnet справляется не хуже Opus. Если пути нет и ошибку
трудно заметить, нужен Opus. Проверка нужна при любой модели: в прогонах порта DeceasedCraft проверяющие нашли ошибки в 20 %
пунктов у исполнителей на Opus.

Модель не задана в вызове, значит агент берёт модель сессии. Обычно это Opus. Поэтому модель указывается в каждом вызове явно.

## 1. Что оставить себе

Главная сессия ведёт разговор с пользователем, принимает решения, собирает итог и делает всё необратимое: установку в рабочую
папку, бэкап, git. Агента не стоит запускать на задачу в 1-3 вызова инструментов: у каждого агента постоянная цена входа
(системный промпт, CLAUDE.md), около 60 тыс. токенов даже на чтение одного файла. Агент с настоящей работой стоит 0,15-0,6 млн
(цифры Claude Code с Claude 5, октябрь 2026; перемерь на своих задачах).
Отдавать агенту стоит то, что займёт много чтения: обход папок и jar, пачку однотипных файлов, независимые части большой задачи,
проверку чужой работы. Мелкие задачи по одной спецификации (в порте DeceasedCraft: теги, рецепты и квесты одного этапа) объединяй
в одного агента: три агента вместо одного - это лишние 120 тыс. токенов входа и три отчёта на сверку.

## 2. Какую модель брать

Колонка «Основание» - что подтверждено в порте DeceasedCraft (2026-10); «не проверено» значит, что рекомендация выведена, а не
измерена. В другом проекте перепроверь на первых прогонах.

| Работа | Модель | Усилие | Основание |
|---|---|---|---|
| Извлечь данные готовым скриптом: профили, логи, подсчёты, ответы по списку вопросов | sonnet | low / medium | проверено: 17 из 17 профилей |
| Обойти файлы и jar по ясным критериям, составить опись (только чтение) | sonnet (тип Explore) | medium | проверено частично |
| Сделать по точной спецификации, когда решения приняты: генератор, теги, KubeJS, квесты, отчёт | sonnet | high | проверено: реальный этап порта (генератор, теги, 3 квеста, отчёт) |
| Простейшее: есть ли файл, сколько строк, совпадает ли хеш, формат JSON | haiku | low | не проверено |
| Нет готового пути: mixin в чужой код, поиск причины бага, дизайн с компромиссами, спорные источники | opus | по умолчанию | опыт порта, не измерено |
| Проверить по чек-листу: сборка, тест, сверка с решениями, сверка с генератором | sonnet | high | проверено: со списком утверждений и усилием high нашёл ошибки исполнителя (раздел 5) |
| Проверить Java / mixin по чек-листу с доступом к jar (javap, исходники) | sonnet | high | проверено: нашёл crash-риск, пропущенный автором |
| Опровергнуть без чек-листа: новый worldgen, необратимое для мира, спорный дизайн | opus | high | применялось: порт и 10 ревью Space Journey (раздел 5), с Sonnet не сравнивалось |

Если Sonnet-агент вернул «не уверен», провалил проверку дважды или оказалось, что готового пути нет, повтори на Opus только этот
пункт, а не весь прогон.

## 3. Что положить в промпт

Агент не видит разговор. Подагент получает те же CLAUDE.md, что и главная сессия: из папки, где открыта сессия, и из папок выше
неё, с импортами, но в том виде, в каком главная сессия прочла их при старте или возобновлении. Новый CLAUDE.md или правка
посреди сессии до её подагентов, в том числе агентов Workflow, не доходят (проверено по записи attachment типа instructions:
2026-10-12 три правки главной сессии через Edit, 2026-10-15 новый файл, 2026-10-23 ни у одного из 39 агентов после правки).
Сжатие контекста (/compact) перечитало правку для главной сессии (2026-10-12, один случай; подагенты после него не проверены).
До перезапуска сессии новое правило пиши в промпт.
Если папка проекта не совпадает с папкой сессии и не лежит выше неё, CLAUDE.md проекта не получит никто: в проекте Space
Journey (2026-10-15) сессия была открыта в папке игры, и текст CLAUDE.md репозитория не попал в начальный контекст ни одного из
журналов агентов (около ста, проверено по записям attachment типа instructions). Тогда открой сессию в папке проекта или положи
в папку сессии CLAUDE.md с импортом `@путь` к проектному (пробел в пути пишется как `\ `). Импорт файла вне папки сессии
загружается, только если у проекта в `~/.claude.json` стоит `hasClaudeMdExternalIncludesApproved: true`; приложение Claude
диалог разрешения не показывает, и без флага импорт молча пропускается. Флаг - настройка безопасности, его ставит пользователь
при закрытом приложении (проверено 2026-10-15: после флага CLAUDE.md проекта дошёл до новой сессии, видно по той же записи). Встроенный агент Explore
CLAUDE.md в начальный контекст не получает: в журнале единственного такого агента (2026-10-13) записи attachment типа
instructions нет, у агентов general-purpose (16 из 16) и Workflow она есть; про Plan это сказано только в справке Claude Code.
Нужное им пиши в промпт. Навыки: в списке подагента они могут быть, но тексты не гарантированы, поэтому не полагайся на них, а дай путь к файлу.

- Цель и признак готовности: что должно получиться и как это проверить делом.
- Решения пользователя дословно, с датой. Пересказ искажает смысл, а агент не может переспросить.
- Пути к нужным SKILL.md и к разделам журнала проекта, которые надо прочитать первыми. Путь к навыку дешевле и точнее пересказа.
- Агенту, который читает исходники чужого мода или библиотеки, дай тег или коммит, из которого собран jar у пользователя, и
  требуй ссылки файл:строка по нему: main бывает далеко впереди релиза (Space Journey 2026-10-14: main Starfold ушёл от тега
  v0.1.1 на 962 файла, PlanetRenderer Cosmonautics нашёлся только в невыпущенном main; оба раза поймал проверяющий).
- Запреты: куда писать нельзя (например, «только во временную папку, в рабочую папку и в запущенную программу не ставить»), какие
  файлы принадлежат другим агентам. Рабочая папка подагента - папка сессии, и команда с относительным выводом пишет туда (unzip без
  -d, jar xf, javac при внутренней ошибке кладёт javac.<дата>.args): дай готовые команды с абсолютной папкой агента (Space Journey:
  2026-10-21 класс Sable лёг в папку игры, 2026-10-25 туда же файл javac).
- Формат ответа через schema: изменённые файлы, запущенные проверки с их выводом, что не сделано, открытые вопросы и «ошибки по
  ходу» (что сорвалось или потребовало обхода, настоящая причина, как обошёл, что бы это предотвратило). Без этого пункта агент
  молча обходит ловушки, и следующий агент наступает на них снова.
  В промпт с schema добавь: цитаты внутри полей - в «ёлочках», пути - с прямыми слэшами, длинный лог или код - путём к файлу,
  а не текстом. Невалидный JSON в StructuredOutput был в 10 вызовах из 421 (2026-10-09..23, DeceasedCraft и Space Journey),
  все в ответах больше 9 тыс. байт, из 75 ответов меньше 5 тыс. не упал ни один. Причина видна в одном (прямая кавычка внутри
  строки), у остальных журнал хранит только первые 2048 знаков; совет о слэшах взят из сообщения об ошибке инструмента. Повтор
  шлёт весь ответ заново, у двух агентов он упал снова.
- Ловушки окружения: общие для проекта держи в CLAUDE.md (его получает каждый подагент, кроме Explore и Plan, если CLAUDE.md
  лежит в папке сессии или выше неё, см. начало раздела; навыки и журналы только по имени);
  в промпт или бриф пиши первым разделом лишь то, чего не было в CLAUDE.md при старте сессии. Агенты пропускают то, что стоит
  в конце.

Общую часть (пути, правила, решения) держи одной константой и добавляй ко всем промптам, а задание каждого агента пиши отдельно.

## 4. Как запускать

- Параллельным агентам давай каждому свою подпапку для временных файлов: в общей папке они затирают друг другу одноимённые
  скрипты (ids.py) и импортируют чужие.
- Agent: `model: "sonnet" | "haiku" | "opus"` и `effort` из таблицы раздела 2 (инструмент Agent принимает его, когда усилие
  велит навык). Независимые агенты запускай одним сообщением, долгие в фоне.
- У ожидания долгого прогона (опыт, серия, фоновая команда) есть предел и действие по нему: снять состояние (стеки потоков,
  хвост лога), погасить дерево процессов (на Windows `taskkill /T /F /PID <pid>`), записать. Тишина дольше обычного - событие,
  а не работа: в Space Journey замер 20 минут ждал признака, который с модом Sodium не наступает, а зависание выхода поймал
  только сторож с пределом 180 с, снявший стеки (2026-10-15..16). Предел ставь в сам прогон: у фоновой команды Bash
  (`run_in_background`) `timeout` не действует (описание инструмента даёт предел только команде на переднем плане; 2026-10-23,
  Claude Code 2.1.308: `sleep 75` с пределом 20 с дошёл до конца). Прогон на часы запускай отдельным процессом (на Windows
  Start-Process), в конце вывода печатай маркер и жди его через Monitor.
- После прогона, который запускал процессы, сверь их список: скрипт, искавший JVM по имени папки, их не гасил, и три
  dev-сервера работали на одном порту (2026-10-15).
- Workflow (только если пользователь согласился на мультиагентную работу): `agent(prompt, {model: 'sonnet', effort: 'medium',
  schema, label, phase})`. Обычная схема: `pipeline(задачи, исполнитель, проверяющий)`. Каждый исполнитель получает свой набор
  файлов, чтобы агенты не правили один файл. Сигнатуры верны для Claude Code на октябрь 2026; при сомнении прочитай навык
  workflow-authoring, если он есть.
- Прогон упал на лимите: запусти заново с `resumeFromRunId` и тем же скриптом. Готовые агенты вернутся из кеша. Если скрипт
  изменился, из кеша вернётся только неизменённое начало: после первого изменённого вызова агенты запускаются заново (2026-10-15:
  изменился текст навыка в промптах части исполнителей; из кеша вернулись только два вызова до первого изменённого, остальные, в
  том числе с неизменёнными промптами, запущены заново).
- Workflow пересылает каждому агенту последнее на момент запуска сообщение пользователя с пометкой, что это запрос, запустивший
  прогон (шапка по-английски: "the user request that triggered this workflow run"; проверено 2026-10-15 по журналам агентов).
  Если пользователь между делом написал о другом, агенты получат это рядом с заданием: исполнители теста навыка получили длинное
  сообщение о системе координат мира, не связанное с заданием, и сообщили о нём главной сессии. Запускай прогон сразу после
  сообщения, к которому он относится. Пояснение в промпте не проверялось, а шапка пересылки велит агенту ставить пересланное
  сообщение выше задания.
- После прогона запиши в журнал, сколько было агентов, на каких моделях и сколько токенов ушло (`totalTokens` в записи прогона).
  Без этих цифр выбор модели в следующий раз будет на глаз.

## 5. Как проверять

- Отчёту агента не верь на слово. Ключевые пункты проверь сам: запусти тест или сборку, посмотри diff, открой файл.
- Проверяющий получает результат исполнителя и задачу найти ошибку. Если пункт не проверен делом, он считается непрошедшим.
  Промпт «подтверди, что всё хорошо» даёт согласие, а не проверку.
- Одного отчёта исполнителя проверяющему мало. Дай ему 5-12 главных утверждений исполнителя (тех, на которых держится
  результат; остальные проверь выборочно сам), команды его проверок и задание повторить сборку или генерацию в чистую папку и
  сравнить. В порте DeceasedCraft (2026-10-13) проверяющие Sonnet medium,
  получившие только отчёт на 40-60 тыс. знаков, проверили делом 8 утверждений из 13. Sonnet high со списком утверждений и
  командами проверили 19 из 21 и нашли две ошибки, которые исполнитель пропустил. Менялись сразу список и усилие, вклад каждого
  отдельно не измерен.
- Свою работу главная сессия отдаёт на проверку так же, как работу исполнителя. В проекте Space Journey (2026-10-15) проверка
  замера, сделанного главной сессией на новом стенде, нашла 9 дефектов, 3 из них меняли выводы; ревью её кода сборки №1 из 15
  находок подтвердило 10, из них 4 важные.
- Большое изменение (новый механизм, сотни строк, необратимое для данных) проверяй состязательно. На каждую область кода
  искатель находок; на каждую находку опровергатель с доступом к коду и заданием доказать, что она неверна, устарела или спорит
  с решением пользователя (CONFIRMED только делом: файл:строка, javap, прогон; иначе REFUTED или UNCERTAIN с прогоном, который
  решит); в конце критик полноты: что не искал никто, в том числе пропуски главной сессии. В Space Journey (10 ревью,
  2026-10-15..23) в первых трёх опровергатели отсеяли 5 из 15, 5 из 11 и 5 из 14 находок, в поздних почти всё подтвердилось;
  критик полноты дважды нашёл главное (падение сервера в тике; «неподвижный» шаблон мира, который менялся) и раз пропуск
  главной сессии (прежние тесты после правок не прогнали). Цена ревью 7-18 агентов, 1,4-3,4 млн токенов, около часа (Claude 5,
  октябрь 2026).
- Если рабочие файлы в это время меняет другой прогон, проверяющие читают замороженный снимок (diff от базы и копии файлов): в
  ревью по рабочему дереву часть находок пришла уже исправленной. Снимок с незакрытой временной правкой (мутацией) негоден.
- Утверждение агента о чужом коде (игра, мод, библиотека) принимай, когда за ним байткод или исходник версии пользователя по
  всему пути вызова, а не сигнатура; о логе - строка лога. Это касается и проверяющих: так оказались неверны «записи публичные,
  правка доступа (AT) лишняя» (они protected), «`difference` работает для любой реализации» (код игры ветвится по классу и
  выгрузил игроку 9 чанков) и «иначе корабли не сохранятся» (мод Sable сохраняет их сам).
- Замечания проверяющих вноси до установки. Если не согласен с замечанием, запиши почему.

## 6. Разбор ошибок

Агент знает о своих ошибках больше всех, поэтому причину спрашивают у него, а не угадывают по итогу.

- Агент вернул ошибку, упал, вернул пустой результат или проверка нашла у него ошибку: продолжи этого же агента через
  SendMessage и попроси короткий разбор: что сорвалось, настоящая причина, как обошёл, что бы это предотвратило. Новую работу при
  этом не давай. Агента, который закончил без ошибок, тоже стоит спросить, если у него было много вызовов: обходы он не всегда
  упоминает сам.
- Если агент умер (лимит, ошибка API) и продолжить его нельзя, прочитай конец его журнала (у workflow: journal.jsonl и
  agent-*.jsonl в папке прогона) и запиши причину сам.
- Раз в этап прогони аудит сбоев по журналам сессии (скрипт отбирает вызовы с ошибкой, в том числе с кодом возврата 0) и сверь с
  записанным. Пример из порта DeceasedCraft: в аудите 2026-10-12 из 27 типов сбоев 12 не были записаны нигде.
- Каждый разбор записывай в журнал проекта или навыка: шаг, причина, тип (ловушка окружения, неясное или неверное задание,
  ограничение модели или инструмента, ошибка в коде), что изменить. Свои ошибки главной сессии записывай туда же.
- Ошибка одного типа встретилась второй раз: это уже не случайность. Исправь источник (бриф, CLAUDE.md, факт в навыке, инструмент)
  или предложи пользователю новый навык через skill-forge. Так система учится, а не повторяет одно и то же.

## 7. Расхождение с решением пользователя

Агент может сделать не так, как решил пользователь: отступить от решения, расширить его или вывести следствие, которого
пользователь явно не решал (пример из порта DeceasedCraft: «зомби в защитном костюме тоже защищены» - вывод, которого
пользователь явно не решал). Такое расхождение не исправляется молча ни в сторону решения, ни в сторону агента: агент мог найти решение
лучше, пользователь мог ошибиться или быть прав.

- Сразу разбери: решение дословно; что сделал или предлагает агент и почему (спроси его через SendMessage, если причина не видна);
  к чему ведёт каждый вариант для результата, рисков и объёма работы; какой вариант рекомендуешь и почему.
- Покажи разбор пользователю одним вопросом с вариантами (AskUserQuestion), рекомендуемый вариант первым.
- Часть, которой касается расхождение, не ставь до ответа. Остальное можно делать дальше.
- Ответ пользователя запиши в журнал проекта как решение, с датой. Если агент оказался прав, это тоже урок: запиши, что
  помогло ему увидеть лучше.
- Чтобы расхождения находились, в промпте исполнителя и проверяющего проси отдельный пункт отчёта: «где результат отличается от
  решений пользователя или выходит за них».

## Ловушки

| Симптом | Причина | Решение |
|---|---|---|
| Все агенты работают на Opus, лимит кончается за один прогон | модель не указана и наследуется от сессии | указывать `model` в каждом вызове |
| Агент нарушает правила проекта или изобретает уже сделанное | навыки и журнал проекта ему не передали | пути к SKILL.md и разделам журнала в промпте |
| Агент поменял рабочие файлы без бэкапа или при запущенной программе | в промпте не было запрета | «только во временную папку», установку делает главная сессия |
| Проверяющий одобрил то, что потом сломалось | его просили подтвердить, а не опровергнуть | «найди ошибку; не проверено делом значит не прошло» |
| Два агента затёрли правки друг друга | общий файл | делить по файлам, при нужде worktree |
| Прогон оборвался на середине | лимит сессии | `resumeFromRunId` |
| Одна и та же ловушка у разных агентов | обходы не попадают в отчёт и в журнал | пункт «ошибки по ходу» в формате ответа, разбор (раздел 6) |
| Агент тихо сделал не по решению или главная сессия тихо «поправила» агента | расхождение не показали пользователю | раздел 7: разбор и вопрос пользователю до установки |
| Отчёт агента не появился, хотя работа сделана | Write у подагента может отказать в файле-отчёте (правило среды: результат возвращается текстом) | результат - текстом или через schema; файл отчёта пишет главная сессия, правило не обходить |
| Повторяются одни и те же сбои окружения у разных агентов | урок записан в журнал или навык, а подагент их не видит, или урок дописан в CLAUDE.md посреди сессии (подагенты получают снимок со старта, раздел 3) | урок в CLAUDE.md или в инструмент проекта (в порте DeceasedCraft: eol.py для окончаний строк, jp.py для javap), до перезапуска сессии тот же урок и в промпты; повторный аудит журналов сессии |
| Агент ищет пути, classpath и т. п. заново | в промпте нет точных подпутей и команд | давать точные пути, готовые строки команд и где лежат ещё не установленные файлы |
| У нескольких агентов сразу кончился GitHub API | лимит без токена (60 запросов в час) общий на IP для всех параллельных агентов | обходы в бриф до запуска: файлы через `raw.githubusercontent.com` или `cdn.jsdelivr.net/gh/<owner>/<repo>@<тег>/<путь>`, списки файлов через `data.jsdelivr.com` (Space Journey 2026-10-14: лимит кончился у всех 7 агентов исследования, у одного примерно через 15 вызовов; DeceasedCraft: у двух) |
| Агент не знает правил проекта, хотя они записаны в CLAUDE.md | сессия открыта не в папке проекта, это агент Explore / Plan, или правило дописано в CLAUDE.md после старта сессии | сессия в папке проекта или CLAUDE.md папки сессии с `@путь`; агентам Explore и Plan правила в промпт; правило, дописанное посреди сессии, - в промпты до перезапуска |
| Агент падает на первом же запросе, без вызовов: "safeguards flagged this message", `[reasoning_extraction]` | вероятно, промпт просит пересказать по шагам, что агент скажет пользователю и что сделает (2026-10-15: 18 из 18 вызовов, Opus и Sonnet; какая часть формулировки виновата, не выяснено) | дать обычную задачу: пробная папка с файлами, ответ пользователю в файл, итог через schema (так прошли все 32 запуска того же теста) |

## Границы

Не нужен для задачи на несколько вызовов, для разговора с пользователем и для решений, которые принимает пользователь. Workflow
запускается, только когда пользователь согласился на мультиагентную работу. В остальных случаях подойдут один-два Agent или
работа самому. Если агенты недоступны (нет Agent / SendMessage, другая среда), сделай задачу сам по тем же пунктам 3 и 5; раздел 4
тогда не применяется. Названия инструментов и цифры токенов относятся к Claude Code; в другой среде перепроверь.
