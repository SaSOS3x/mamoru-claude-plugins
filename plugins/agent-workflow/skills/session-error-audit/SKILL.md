# Аудит ошибок сессии

Агенты в одном проекте наступают на одни и те же грабли, потому что урок записан там, куда они не смотрят. Подагент гарантированно
получает только CLAUDE.md, и то лишь из папки, где открыта сессия, и папок выше неё; встроенные Explore и Plan не получают его в
начальный контекст (Explore проверен по журналу агента 2026-10-23, Plan только по справке Claude Code; env из `.claude/settings.json` на подагентах отдельно не проверено). Журналы, HANDOFF и навыки он читает, только если их назвали в промпте. Аудит
отвечает на три вопроса: что падало (счёт по причинам), записано ли это там, где увидит каждый агент, и что исправить у источника.

Порядок важен. Сначала считаем по журналам сессии скриптом (2 секунды, без токенов), потом сверяем с записями, потом чиним
источник, и только в конце, если ничего другого не помогло, пишем правило или навык.

## Когда запускать

- Раз в этап проекта и после большой задачи или workflow с агентами.
- Когда пользователь просит: "проверь ошибки сессии", "аудит ошибок", "почему агенты повторяют ошибки".
- Когда один и тот же сбой замечен в отчётах агентов второй раз.

Не запускай посреди работы над задачей: аудит читает уже законченные вызовы, а свежий хвост сессии почти весь состоит из
вызовов самого аудита.

## Цикл

### 1. Собрать (scan_fail.py)

```
python -I -X utf8 "${CLAUDE_SKILL_DIR}/scripts/scan_fail.py" --project "<папка проекта>" --out <рабочая папка>
```

`--project` берёт папку проекта и сам находит журналы в `~/.claude/projects/<имя>` (имя = путь, где каждый знак кроме
букв и цифр заменён на `-`; работает с `C:\...`, `C:/...` и Linux-путями). Если не нашёл, дай `--dir` с папкой журналов.
`--session <id>` берёт одну сессию, `--since` / `--until` (UTC, лучше полная метка `2026-10-12T00:00:00Z`; принимаются
также дата `2026-10-12`, `...T23:11Z`, `...+00:00`) режут период; время разбирается как время, а не как текст, мусор вместо
времени останавливает скрипт с кодом 2. Скрипт читает основной
`*.jsonl` каждой сессии и все `<id>/subagents/**/agent-*.jsonl` (включая агентов workflow; папка подагентов, у которой основной
журнал уже удалён, читается как отдельная сессия), сопоставляет каждый вызов с его
результатом (только записи `assistant` и `user`, каждый id один раз) и записывает строку, если результат ошибочный
(`is_error`), начинается с `Exit code` не 0 или содержит Traceback, No such file, SyntaxError, denied, `delimited by
end-of-file` (обрезанная длинная команда Bash, код 0), исключение Java (`Exception in thread`, `Caused by:`) и подобное.
Результат: `rows.json`, `scan_meta.json`. Если найдено 0 вызовов, скрипт печатает WARNING: это не "сбоев нет", а неверный период, `--session` или `--dir`. Пути вида `/c/...` скрипты на
Windows сами превращают в `C:/...`; неверный ввод (нет папки, плохое время, плохой файл `--rules`) даёт строку `ERROR:` и
код 2, без Traceback.

### 2. Разобрать (classify.py и show.py)

```
python -I -X utf8 "${CLAUDE_SKILL_DIR}/scripts/classify.py" --dir <рабочая папка> [--rules свои_правила.json]
python -I -X utf8 "${CLAUDE_SKILL_DIR}/scripts/show.py" --dir <рабочая папка> --cat "unclassified"
```

Каждая строка получает один из трёх видов. Настоящий сбой делится на жёсткий (код возврата не 0) и мягкий (код 0, но в
выводе Traceback или No such file). Ожидаемое (EXPECTED) - нормальный ответ проверки: grep без совпадений, diff с различиями,
офлайн-тест, который поймал настоящее расхождение. Шум (NOISE) - слово из шаблона в успешном выводе или содержимое прочитанного
файла.

`show.py` показывает в каждой строке часть вывода с ошибкой (строки вокруг последнего маркера ошибки, а не начало), поэтому
команда, которая сначала напечатала файл, а потом упала, видна по ошибке; `--part head` вернёт начало вывода.

После таблицы обязательно посмотри глазами (`show.py --cat ... --n 5`) самый большой кластер, всё в
`unclassified-strong` и по две-три строки из каждого кластера, на который будешь опираться: шаблоны ловят слова, а не смысл.
Для причин, свойственных проекту, добавь свои правила в JSON (`where`: `out`, `cmd` или `tool:Имя`). Нераспознанное, которое
повторяется, получает правило, чтобы в следующем аудите не разбирать его заново.

### 3. Сверить с записями

Сначала, до таблицы, проверь, что CLAUDE.md проекта вообще доходит. Он доходит, только если папка проекта это папка сессии или
лежит выше неё (или CLAUDE.md папки сессии импортирует его через `@путь`, а пользователь разрешил внешние импорты; см. agent-delegation). В
проекте Space Journey (2026-10-15) сессия была открыта в папке игры, и текст CLAUDE.md репозитория не попал в начальный контекст
ни одного из журналов агентов (около ста): все записи "есть в CLAUDE.md" там не доходили. Проверка: в журнале агента загруженные
файлы инструкций лежат в записи `type: attachment` с `attachment.type` `instructions`; ищи там строку из CLAUDE.md проекта.

Потом для каждого настоящего кластера крупнее двух-трёх случаев ответь на два вопроса. Записано ли это вообще (Grep по CLAUDE.md,
HANDOFF "Facts", журналам навыков, `.claude/skills/*/SKILL.md`)? Доходит ли запись до каждого подагента? Доходят: CLAUDE.md
проекта (если прошёл проверку выше; Explore и Plan его не получают), сам инструмент (скрипт в проекте, который агент вызывает).
`.claude/settings.json` (env, hooks, permissions) на подагентах отдельно не проверен. Не доходят: журналы, HANDOFF, навыки, не
названные в промпте. Запись вне этого списка считай отсутствующей. CLAUDE.md агенты получают в том виде, в каком сессия прочла
его при старте или возобновлении: правку посреди сессии её агенты не увидят до перезапуска сессии, поэтому то же правило клади в
их промпты (три случая 2026-10-12..23 по записи attachment типа instructions, подробно в agent-delegation, раздел 3). Итог -
таблица "ошибка | сколько раз | где записано | доходит до агентов | что чинить".

Второй источник ошибок скрипт не видит: то, что не дало упавшего вызова. Это неверные допущения о чужом коде, пробелы в
проверке, находки проверяющих и то, что заметил пользователь. Их бери из дневника проекта (поля "Проблемы", "Урок"), из отчётов
проверяющих и из реплик пользователя. Реплики, отправленные во время работы, лежат в журнале сессии не в записях `type: user`, а
в записях `type: queue-operation` с `operation: enqueue` (текст в `content`) и в `attachment` типа `queued_command`
(`attachment.prompt`; бери те, у которых `origin.kind` равен `human`, остальное уведомления задач). В Space Journey за
2026-10-14..15 скрипт отнёс к настоящим 59 сбоев из 2101 вызова (проверка глазами нашла ещё 4 спрятанных и одну ложную), и стоили
они по лишнему вызову, а самые дорогие ошибки шли этим вторым путём (например, все dev-клиенты до исправления шли без Sodium).

Это шаг суждения, не подсчёта. Его делает главная сессия или один агент среднего уровня со схемой ответа и списком файлов для
чтения; результат всё равно просмотри сам.

### 4. Исправить источник, потом записать правило

Порядок по пользе, сверху вниз; останавливайся на первом, что убирает ошибку.

1. Убрать причину: переменная окружения в `.claude/settings.json`, установленный модуль, права, hook, маленький инструмент
   вместо угадывания (в проекте DeceasedCraft: `python _port/tools/jp.py <класс>` убрал "class not found" в javap, `eol.py`
   показывает окончания строк по байтам). Меняющее настройки делает пользователь или с его явного согласия.
2. Короткий блок в CLAUDE.md (до 15 строк): правило, число случаев, пример. Только то, что должно дойти до каждого агента.
   До перезапуска сессии её агенты новый блок не получат: в этой сессии то же правило клади в их промпты.
3. Дополнить существующий навык, если ошибка связана с его областью.
4. Новый навык только по правилам skill-forge: задача повторяется, без подсказки решается плохо, есть проверенный способ. Навык
   про ловушки окружения не создаётся: правило должно доходить до каждого подагента, а навык доходит не всегда.

Ничего из этого не применяй без пользователя: это инструкции для всех следующих сессий. Положи предложения в `skills-lab/`
или покажи списком и жди ответа.

### 5. Записать в журнал

Запись "анализ" в журнал проекта: период, сколько вызовов, сколько настоящих сбоев (жёстких / мягких), топ кластеров, что
решено чинить. Положи `summary.json` и `scan_meta.json` аудита в `audit-baseline/<дата>/` рядом с журналом проекта (не в папку
навыка: в плагине она обновляется вместе с навыком): журналы сессий со временем чистятся, а сравнивать со старым счётом нужно.

### 6. Повторить на следующем этапе и сравнить

```
python -I -X utf8 "${CLAUDE_SKILL_DIR}/scripts/compare.py" --old <папка журнала проекта>/audit-baseline/<дата прошлого аудита> --new <рабочая папка>
```

Печатает по кластерам было / стало, число сбоев на 1000 вызовов, новые и исчезнувшие кластеры. Кластер упал - правка сработала.
Кластер остался - правило не доходит до агентов или чинит не то (вернись к шагу 3). Новый кластер - новый вид ошибки, разбери
его так же. Сравнивай на 1000 вызовов, а не абсолютные числа: объём работы за этап разный.

## Что показал первый аудит (DeceasedCraft, 2026-10-12, пример для ориентира)

Период 8-11 октября 2026, 108 файлов журналов, 8799 вызовов, 708 подозрительных строк. Настоящих 332 по первому аудиту
(138 жёстких + 194 мягких); скрипты навыка на том же периоде дают 719 строк и 339 настоящих (138 + 201): 4 мягкие строки -
вывод самих скриптов аудита, теперь это шум, ещё одна - обрезанная длинная команда, которую первый аудит не видел (правило
2026-10-25), ещё 10 - Java-программы, упавшие с кодом 0 (правило 2026-10-27). Ожидаемых 42, шума 338. Мягкие сбои - около
59 % настоящих: код возврата цепочки с `;`, `| head`,
`2>&1` или циклом скрывает ошибку, поэтому проверять надо вывод.

## Ловушки самого аудита

- Мягкий сбой не виден по коду возврата. Без разбора текста (шаблоны `SOFT` в classify.py) аудит найдёт только 41 % (138 из 339).
- Java-программа, запущенная с `| tail` или в цепочке с `;`, падает с кодом 0: исключение видно только в выводе
  (`Exception in thread`, `Caused by:`). Сбоем такая строка считается, только если команда сама запускала java, javac или
  gradlew; иначе это цитата лога (в логах Minecraft `Caused by:` повсюду), и она идёт в шум. 2026-10-27: аудит вехи пропустил
  так `ClassNotFoundException` офлайн-проверки; по всем журналам папки игры правило нашло 18 таких падений.
- Аудит ловит собственный вывод: агент, запускающий скрипты аудита, печатает цитаты ошибок (UnicodeEncodeError, Traceback) и
  создаёт ложные строки. Мягкие строки команд, где упомянуты `scan_fail.py`, `rows.json` и т. п., скрипт уже относит к шуму.
  Такие же цитаты дают `cat` / `sed` журналов проекта; их скрипт нарочно не прячет, чтобы не скрыть настоящую ошибку фоновой
  задачи в `cat` её вывода. Смотри их глазами и добавляй правило на команду.
- Искать журналы только в корне папки проекта нельзя: журналы подагентов лежат в `<id сессии>/subagents/**`, и в первом
  проекте DeceasedCraft это 107 файлов из 108.
- Ожидаемое не равно ошибке: `grep` без совпадений тоже даёт код 1. Не добавляй такие строки в счёт и не "чини" их.
- Шаблоны построены под Git Bash / PowerShell на Windows и английские сообщения. Для другой оболочки или языка вывода часть
  строк окажется в `unclassified-strong`: прочитай их и добавь правила.
- Формат журналов меняется с версиями Claude Code. С 2.1.304 (2026-10-21) журнал хранит копии вызовов в записях
  `api-request-blob` без метки времени. Они проходят через любой `--since` / `--until`, и с каждой новой сессией их больше:
  старый scan_fail.py на периоде паспорта насчитал вместо 8799 вызовов 9944 (2026-10-23) и 10 089 (2026-10-25), настоящих
  363 вместо 328 при тех же правилах. После обновления Claude Code повтори сохранённую базу (см. «Проверка результата»). Если
  числа разошлись больше чем на несколько строк, скрипт читает записи нового вида: найди их до сравнения этапов.
- Журналы сессий чистятся по настройке Claude Code; старый счёт после чистки не восстановить, поэтому `summary.json` хранится.

## Проверка результата

Таблица в конце `classify.py` сходится: настоящие + ожидаемые + шум = число строк в `rows.json`, `unclassified-strong` равен нулю
или разобран. В каждом кластере, на который опираешься, глазами проверены 2-3 строки. Для повтора аудита на том же периоде:
`--since` и `--until` из старого `scan_meta.json`, причём `--until` бери из поля `last_ts` (полная метка, например
`2026-10-15T11:48:20.551Z`). Поле `until` бывает позже самого аудита, и тогда в повтор попадает работа после него (база
Space Journey 2026-10-15: 3184 вызова вместо 2101). Числа совпадают с точностью до нескольких строк.

## Границы

Навык считает сбои вызовов инструментов; ошибки без упавшего вызова собираются вручную (шаг 3). Он не оценивает качество самих навыков (описания, ссылки на файлы, смесь метода с
состоянием проекта): для этого есть проверка по skill-forge, шаг "Сопровождай". Он не заменяет раздел "ошибки по ходу" в отчётах
агентов: тот сообщает причину сразу, аудит видит только то, что упало. Если нужен один сбой, а не сводка, читай журнал сессии
напрямую.

в репозитории маркетплейса, база первого аудита рядом в `baseline/2026-10-12/`.
Проверен: 2026-10-12, Windows 11, Git Bash + PowerShell, Python 3.14.7, Claude Code (журналы сессии Opus 5.5 + агенты Sonnet 5.5).
Скрипты прогнаны на журналах проекта (9118 вызовов, 108 файлов, 2 секунды): за период первого аудита (до 2026-10-11T23:11:00Z,
полная метка; короткая `23:11Z` после правки даёт те же числа)
708 строк (как в первом аудите), настоящих 328 (138 жёстких, 190 мягких) против 332 (138 / 194), ожидаемых 42, шума 338
против 334. Сравнение двух прогонов compare.py и опции --rules, --session, --dir проверены; на подагентах и других ОС нет.
Повторно 2026-10-25 после правки копий вызовов и двух новых правил (журналы Claude Code до 2.1.308): период паспорта 8799
