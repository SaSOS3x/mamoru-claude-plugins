# История изменений: windows-shell-claude-code

Что менялось в навыке, когда и почему. Новые записи добавляются в конец. Подробный журнал разработки лежит в проекте, где навык
делали: `_port/skills-lab/windows-shell-claude-code/JOURNAL.md` порта DeceasedCraft. В плагин он не входит.

## 2026-10-12 | Первая версия
Что: ловушки Git Bash, python.exe и JDK на Windows, а также скрипты env_probe.py, eol.py и classpath_jar.py.
Почему: аудит ошибок агентов в порте нашёл 331 упавший вызов. Больше всего было кавычек и heredoc, путей `/c/`, cp1251,
обманчивых кодов выхода и javap без полного classpath.
Проверено: 20 проверок на ПК. Исполнитель с чистым контекстом навык ещё не проходил.

## 2026-10-12 | Скрипты через переменную папки навыка
Что: все вызовы скриптов идут через переменную папки навыка.
Почему: плагин читается не из папки маркетплейса, а путь к нему зависит от способа установки.

## 2026-10-12 | Исправления по проверке плагинов
Что: `python -I -X utf8` вместо `python -I`. env_probe.py даёт WARN для несуществующей папки. classpath_jar.py сообщает об
отсутствующих jar и `@файле`. Про PYTHONIOENCODING сказано для любого проекта.
Почему: независимая проверка (plugin-check, 2026-10-12). `-I` отключает все переменные PYTHON*, и вывод оставался в cp1251.
env_probe писал OK для несуществующей папки, а classpath_jar молча пропускал пути.
Проверено: `PYTHONUTF8=1 python -I` даёт utf8_mode 0, `python -I -X utf8` даёт 1. Повторная проверка подтвердила каждый пункт.

## 2026-10-12 | Причина в паспорте записана словами
Что: строка «Изменения» паспорта.
Почему: подстановка переменной превращала её в путь к кэшу, а причина «плагин работает из кэша» оказалась неточной.

## 2026-10-12 | Исправления по повторной проверке
Что: eol.py называет BINARY файл с байтами NUL, а UTF-16 с BOM раскодирует и считает как текст. У всех трёх скриптов есть
`--help`. classpath_jar.py без Traceback, если нет папки для out.jar. В ловушке 9 сказано, когда нужен `--skip-missing`.
Почему: повторная проверка (plugin-recheck, 2026-10-12). Двоичный файл назывался MIXED, текст с NUL назывался CRLF,
а `--help` env_probe принимал за имя папки.
Решение, которое не нужно отменять: env_probe.py выходит с кодом 0 и при WARN. Это отчёт, а не проверка: на обычном ПК с
Windows какой-нибудь WARN есть всегда, и код 1 рвал бы цепочки `&&`. Проверка отметила код 0 как недочёт, но так задумано.
Проверено: тест из 26 случаев на пробных файлах (журнал agent-delegation, 2026-10-12).

## 2026-10-12 | Паспорт «Проверен» и строка jar в env_probe.py
Что: в паспорте записаны две независимые проверки плагинов (подагенты с чистым контекстом прогнали скрипты по тексту навыка).
env_probe.py печатает путь к jar без заглушки `(see path)`.
Почему: повторная проверка заметила, что паспорт после переноса истории в CHANGELOG остался старым («не прогнан исполнителем»),
а заглушка выглядела как недоделка. Версию jar не спрашиваем, потому что у jar нет `-version`, а папка JDK видна в пути.
Проверено: env_probe.py запущен после правки.

## 2026-10-13 | `-I` отключает пакеты пользователя
Что: в ловушке 3 добавлено, что `python -I` не видит пакеты из `pip install --user` (Pillow, openpyxl), и когда ставить `-I`:
только для файлов, которые агент скачал или распаковал из сети (так требует окружение Claude Code), не для файлов проекта.
В описании навыка добавлен симптом ModuleNotFoundError после python -I.
Почему: на этапе v35 порта DeceasedCraft 3 агента из 8 споткнулись о `-I`: двое получили ModuleNotFoundError для PIL, третий
снова cp1251. Окружение Claude Code просит `-I` для скачанных файлов, а агенты ставили его на все скрипты. Прежняя запись про
`-I -X utf8` чинила только кодировку. Пользователь одобрил правку 2026-10-13.
Проверено: на этом ПК `python -I -X utf8 -c "import PIL"` и `import openpyxl` дают ModuleNotFoundError, `sys.flags.no_user_site` 1;
без `-I` оба пакета находятся в `%APPDATA%/Python/Python314/site-packages`.
Не принято: `python -P` (часть `-I`) тоже не даёт импортировать подложенный `json.py` из папки скрипта и при этом видит Pillow
(проверено). Но окружение Claude Code прямо требует `-I` для скачанных файлов, и навык не должен учить обходить это требование.
Поэтому для скачанных файлов с пакетом pip решает пользователь.

## 2026-10-15 | /c/ из переменной, CRLF от Python, запятая ru-RU, удаление в PowerShell, javap
Что: ловушка 2 дополнена путём /c/ из переменной оболочки, подставленным в код; ловушка 6 - тем, что Python на Windows пишет CRLF
(правку LF-файла писать с newline). Новые ловушки 11 (запятая в дробных числах при ru-RU) и 12 (Remove-Item в инструменте
PowerShell). Строка проверки про javap больше не говорит, что "class not found" всегда значит неполный classpath.
Почему: аудит Space Journey 2026-10-15. Все 7 случаев "class not found" были с полным classpath (имя класса, флаг, -cp после cd),
и прежняя строка вела не туда. Путь /c/ в переменной сломал Python дважды при загруженном навыке. Скрипт Workflow не запустился
после правки Python-ом ("control characters", 112 знаков CR). CSV замера разъехался из-за запятой. Remove-Item в длинной команде
песочница отказала 2 раза из 3, отдельные литеральные команды прошли 4 из 4.
Проверено: на этом ПК 2026-10-15: R=/c/Users и exists в коде даёт False, отдельным аргументом True; '{0:F1}' -f 1.5 и
(1.5).ToString() дают 1,5, InvariantCulture 1.5; Remove-Item и javap по журналам сессии; `&&` в PowerShell 5.1 даёт ошибку разбора (проверено). В той же сессии главная сессия с
загруженным навыком сама попала в ловушку 1 (двойная обратная косая в heredoc для python дошла одинарной), правило верное,
дисциплина его соблюдать слабее. Разбор: `_project/skills-lab/a1-2026-10-15.md` и `_project/JOURNAL.md` проекта Space Journey.
