# Оболочка Claude Code на Windows: Git Bash, python.exe, JDK

Инструмент Bash здесь это Git Bash (MSYS), а `python`, `java`, `javap` это родные Windows-программы. Ловушки лежат на стыке:
Git Bash переписывает часть аргументов, Windows не знает путей `/c/...`, консольная кодировка cp1251, у командной строки лимит.
Основное проверено на этом ПК 2026-10-12 (Git Bash MINGW64, Python 3.14.7, JDK 21.0.8 и 17); пункты с датой 2026-10-15 проверены
в тот день (2, 6, 11 и `&&` в PowerShell командами, 12 и javap по журналам сессии Space Journey), с датой 2026-10-23 - командами
при разборе журналов Space Journey; непроверенное помечено.
Числа "N сбоев" это аудит 331 упавшей команды из проекта DeceasedCraft (не пересчитаны мной).
Граница с `windows-shell-dev`: тот навык про написание и отладку файлов .bat/.cmd, этот про то, как агент запускает команды.

## Порядок работы
1. В новом проекте первой командой: `python "${CLAUDE_SKILL_DIR}/scripts/env_probe.py" [папка со скриптами]`. Строки WARN это
   ловушки, которые сработают именно здесь (кодировки, python3, JDK, имена модулей в указанной папке). Код возврата 0 и при
   WARN: это отчёт, а не проверка (на обычном ПК с Windows какой-нибудь WARN есть всегда), поэтому читай строки WARN.
2. Скрипт длиннее 5 строк или с `\`, `'`, `"` внутри: Write в scratchpad сессии, потом `python путь/к/файлу.py`.
   Правка существующего файла: Edit, не питоновский replace. Edit и Write отказывают (`has not been read`, `modified since
   read`), если файл не прочитан через Read в этом контексте или изменён после чтения. Чаще всего это сжатие контекста: Claude
   Code забывает, что файл прочитан, а `sed -n` и `cat` отметку не возвращают (27 из 32 отказов `has not been read` в главной
   сессии Space Journey 2026-10-16..23; всего там 46 отказов на 614 Edit/Write, у подагентов 0 на 264). Поэтому читай через
   Read (offset/limit), а не `sed -n` или `cat`, и перечитывай после сжатия контекста, правки скриптом, `sed -i` и git.
3. Все пути для python/java: `C:/Users/...` (прямые слэши, с буквой диска). Не `/c/...`, не `/tmp`.
4. Результат оценивай по тексту вывода и по наличию файла, не по коду выхода (ловушка 4).
5. Java: нужный JDK по полному пути; длинный classpath через файл (ловушка 8-9).
6. Всё новое, что стоило больше двух попыток, допиши в этот навык через skill-forge (журнал, потом предложение).

## Ловушки: симптом, причина, что делать
1. **Кавычки и heredoc (47 сбоев).** Симптом: `SyntaxError: (unicode error) 'unicodeescape'`, `unexpected EOF while looking
   for matching`. Воспроизведено: в `python - <<'EOF'` и в `python -c "..."` пара `\\` доходит до Python как `\`
   (`"C:\\x"` стало `"C:\x"`). Команда Bash длиннее примерно 7,2 тыс. знаков (знаков, не байт) ломается при любых кавычках
   (2026-10-23, Claude Code 2.1.308: так упала и команда в 8,9 тыс. знаков без единой кавычки). Обычно это `unexpected EOF while
   looking for matching`, и ничего не выполнено; иногда хвост молча отрезан: `warning: here-document at line N delimited by
   end-of-file`, код 0, начало выполнено (2026-10-09 `cat > mr.py <<'EOF'` оставил 50 строк файла). За 2026-10-08..22 из 20
   таких команд сломались 19. Делай: код и любой длинный текст, в том числе `cat > файл <<'EOF'`, пиши в файл через Write.
2. **Пути /c/ (20 сбоев).** `os.path.exists('/c/Users/Alexandr')` даёт False (Windows читает как `C:\c\Users\...`).
   Git Bash сам превращает в `C:/...` только целый аргумент командной строки (`/c/x`, `--cp=/c/x`, `/tmp`), и то без
   апострофа: `/c/.../it's/x` и `--out=/c/.../it's/x` доходят как есть (проверено 2026-10-23; пробел без апострофа перевод не
   ломает), а это любой путь в `Mamoru's Projects`;
   НЕ превращает пути внутри кода и файлов Python и в списках через `;` (`/c/a;/c/b` дошло как есть). То же со значением
   переменной оболочки, подставленным в код: `R=/c/Users; python -c "...exists('$R')"` даёт False, а `"$R"` отдельным
   аргументом доходит как `C:/Users` (проверено 2026-10-15). Делай: давай переменной значение с `C:/` (`R=C:/Users`) или передавай
   путь Python отдельным аргументом `"$R"`.
   `/tmp` для Python это `C:\tmp`, а для Git Bash `%TEMP%`: два разных места, используй scratchpad.
   `glob('C:/x/*/')` возвращает `C:/x\dir\`: обрезай `rstrip('/\\')` перед `basename`.
3. **Кодировка (23 сбоя).** Без настройки stdout это cp1251: `print('\u2192')` даёт UnicodeEncodeError.
   `PYTHONIOENCODING=utf-8` чинит только stdout/stderr. `open()` без `encoding=` остаётся cp1251 (проверено): UTF-8 файл
   читается МОЛЧА с мусором (`привет` стало `РїСЂРёРІРµС‚`), запись `→` падает. Всегда `encoding='utf-8'` в open/read_text/write_text.
   Проверь `env_probe.py`: стоит ли `PYTHONIOENCODING` в вашей сессии. Задать его можно в блоке `env` файла `.claude/settings.json`
   проекта или `~/.claude/settings.json` (только с согласия пользователя); у каждого проекта он свой, по умолчанию его нет.
   **Конфликт с `-I`:** `python -I` игнорирует ВСЕ переменные `PYTHON*` (проверено: `PYTHONUTF8=1 python -I` даёт
   `sys.flags.utf8_mode` 0, вывод остаётся cp1251), а `python -I -X utf8` даёт 1. Где нужен `-I`, пиши `python -I -X utf8`
   (флаг `-X utf8` не зависит от окружения; в этом режиме `open()` тоже UTF-8). `PYTHONUTF8=1` чинит оба случая, но ломает `subprocess(text=True)` для консольных
   программ Windows: их вывод в cp866, получается UnicodeDecodeError (проверено на `net helpmsg 2`). Такой вывод
   читай байтами: `.decode('cp866', errors='replace')`. Менять переменные окружения без согласия пользователя нельзя.
   **`-I` отключает и пакеты пользователя** (`pip install --user`, здесь Pillow и openpyxl): `ModuleNotFoundError: No module
   named 'PIL'` (проверено 2026-10-13, `sys.flags.no_user_site` 1). Окружение Claude Code просит `-I` для скачанных файлов, и
   агенты переносят это на всё подряд: в одном этапе порта DeceasedCraft так споткнулись 3 агента из 8. `-I` нужен там, где
   его требует окружение: скрипт читает файлы, которые агент сам скачал или распаковал из сети. Файлы проекта и пользователя
   (его моды, его данные, свои черновики) к ним не относятся, такие скрипты запускай без `-I`. Если скрипту по скачанным файлам
   нужен пакет pip, не снимай `-I` сам, а спроси пользователя.
4. **Код выхода врёт (59 % сбоев имели exit 0).** `cmd | head`, цепочка через `;`, `2>&1`, цикл дают код последней команды.
   Проверено: `python нет.py | head` даёт 0 (`${PIPESTATUS[*]}` показывает `2 0`); `set -o pipefail` даёт 2.
   Делай: читай вывод на `Traceback|Error|Exception|No such file|not found|cannot|Argument list too long`,
   проверяй, что нужный файл создан и не пуст; в цепочках используй `&&`.
5. **`python3` это заглушка Microsoft Store** (печатает `Python`, код 49). Вызывай `python`. Скрипты с `python3` в шебанге
   запускай как `python script.py`.
6. **CRLF.** `grep -c $'\r' file` печатает 0 на файле с CRLF (проверено: 3 строки CRLF, ответ 0). Считай по байтам:
   `python "${CLAUDE_SKILL_DIR}/scripts/eol.py" файлы` (CRLF / LF / CR, BOM, MIXED) или `tr -cd '\r' < file | wc -c`.
   Файл с байтами NUL eol.py называет BINARY и окончания не считает. Исключение: UTF-16 с BOM (так пишет `>` в Windows
   PowerShell 5.1), такой текст он раскодирует и считает как обычный. Python на Windows сам пишет CRLF: `open(p, 'w')` и
   `Path.write_text` переводят `\n` в `\r\n`, и прочитанный LF-файл при записи назад тоже становится CRLF. Файл, который должен
   остаться LF, пиши через `open(p, 'w', newline='')` (или `newline='\n'`). Так файл-скрипт для инструмента Workflow, переписанный
   Python-ом, получил CR, и Workflow отказал: "script contains control characters" (2026-10-15).
7. **Имя скрипта = имя модуля stdlib.** `json.py`, `struct.py`, `types.py`, `random.py` рядом со скриптом или в текущей
   папке (даже для `python -c`) перекрывают настоящий модуль: `AttributeError: module 'json' has no attribute 'dumps'`,
   сломанный `zipfile`. Не называй так черновики; `python -I -X utf8` (изолированный режим) игнорирует и папку скрипта, и текущую (а `-I` без `-X utf8` оставляет cp1251, см. ловушку 3).
8. **Не тот JDK.** Здесь `JAVA_HOME` (Machine) = jdk-17, `java` и `javac` на PATH = 21 (заглушки `Common Files/Oracle/Java/javapath`),
   `javap` и `jar` = 17 (Adoptium). Класс, собранный `javac` 21, не запускается через `$JAVA_HOME/bin/java`:
   `UnsupportedClassVersionError ... 65.0 ... up to 61.0` (проверено). Gradle/Maven берут `JAVA_HOME`.
   Делай: полный путь `"C:/Program Files/Java/jdk-21/bin/javap.exe"`, для сборки `JAVA_HOME="C:/Program Files/Java/jdk-21" команда`.
   `javap` 17 тривиальный класс 21 прочитал; на реальных классах модов это не проверено, лучше брать javap 21.
9. **Лимит командной строки ~32 тыс. знаков.** `java -cp <37 тыс.>` даёт `Argument list too long` (код 126; через `| head` виден 0).
   Разделитель classpath на Windows `;`, пути `C:/`. Для `java` и `javac`: `@файл` с аргументами (проверено) или переменная
   `CLASSPATH` (37 тыс. прошло). У `javap` `@файл` НЕ работает (`class not found: @cp2.args`):
   `python "${CLAUDE_SKILL_DIR}/scripts/classpath_jar.py" cp.jar @jars.txt` собирает jar с `Class-Path` в манифесте, дальше `javap -cp cp.jar класс`
   (проверено: 522 записи, 70 тыс. знаков манифеста, класс из последнего jar найден; папки и glob тоже годятся).
   Несуществующий путь в списке останавливает сборку (код 1, jar не пишется): так устаревший `jars.txt` не даёт молча неполный
   classpath. Если старые строки в списке ожидаемы, добавь `--skip-missing`, тогда будут только предупреждения.
10. **Мелочи инструментов.**
    - `cat -n a b` нумерует сквозь файлы: ссылки на строки бери из `grep -n` или Read одного файла.
    - В Git Bash есть `unzip`, нет `zip` (проверено): `python -m zipfile -c`. У этого `unzip` (UnZip 6.00) `*` в шаблоне не
      проходит через `/`: `unzip x.jar 'net/minecraft/*'` берёт только файлы прямо в этой папке, с кодом 0 и без сообщений (36
      из 7936 class-файлов на jar клиента 1.21.1, проверено 2026-10-23). Пиши `'net/minecraft/**'` и сверяй
      `find <папка> -type f | wc -l` с `unzip -Z1 x.jar | grep -c '^net/minecraft/.*[^/]$'` (без `[^/]$` считаются и записи
      папок). Длинные пути тут ни при чём (`**` распаковал и путь в 313 знаков), хотя неполную распаковку дважды списали
      на MAX_PATH.
    - Read режет файл больше 25 тыс. токенов: offset/limit (из журнала, 2 раза).
    - Write у подагента отклоняет файлы, похожие на отчёт: `Subagents should return findings as text, not write report files`
      (4 отказа 2026-10-10..21, все `.md` с report или summary в имени, один был входом для другого скрипта; README.md,
      TASKS.md, plan.md прошли). Это правило среды, оно есть и в системном промпте подагента: верни результат текстом или через
      schema и не обходи правило через Python (agent-delegation, ловушка «Отчёт агента не появился»).
    - git: пути длиннее 260 знаков (клон в scratchpad, сама папка около 160) дают `Filename too long`, хотя Windows их
      пропускает (LongPathsEnabled=1), и `git add` пропускает такой файл с одним предупреждением и кодом 0 (проверено
      2026-10-23, Git 2.56; 3 случая 2026-10-14): пиши `git -c core.longpaths=true ...`. Исключение в pathspec пиши длинной
      формой `':(exclude)путь'`: короткая `':!путь'` на пути, который начинается с `_`, даёт `fatal: Unimplemented pathspec
      magic '_'` (код 128, проверено 2026-10-25).
    - curl сам, а не Git Bash, читает `[]` и `{}` в URL как шаблоны: `[..]` останавливает его (код 3, `bad range
      specification`, ничего не отправлено), а `{x}` молча заменяется на `x`, и запрос уходит по другому адресу (проверено
      2026-10-23, curl 8.22.0). Пиши `curl -g ...` или `curl -G --data-urlencode 'k=[...]'`.
11. **Запятая в дробных числах (локаль ru-RU).** В PowerShell `'{0:F1}' -f 1.5` и `(1.5).ToString()` дают `1,5`, а
    `[string]1.5` и `(1.5).ToString([cultureinfo]::InvariantCulture)` дают `1.5` (проверено 2026-10-15). Java `String.format`
    без `Locale.ROOT` тоже ставит запятую: в проекте Space Journey CSV замера из-за этого разъехался по столбцам. Числа в файлы
    пиши через `Locale.ROOT` в Java и InvariantCulture в PowerShell.
12. **Удаление в инструменте PowerShell.** Защита инструмента отклоняла `Remove-Item` в длинных командах из нескольких операторов
    ("Remove-Item on system path ... is blocked", 2 из 3 таких команд), а отдельные команды `Remove-Item -LiteralPath "<полный
    путь>" -Recurse -Force -Confirm:$false -ErrorAction Stop` с литеральным путём в двойных кавычках прошли 4 из 4 (2026-10-15, по
    журналу сессии Space Journey; причина отказа не выяснена). Путь с апострофом (`Mamoru's Projects`) бери только в двойные
    кавычки. Удаляй отдельной командой только то, что создал сам; запрет среды не обходи через Python или Bash, а скажи
    пользователю.

## Проверка результата
- `env_probe.py` без WARN, которые касаются вашей команды; после своего скрипта: файл существует, размер больше 0, в выводе
  нет `Traceback`.
- Для javap: сначала `javap -cp cp.jar известный.класс`, потом нужный. "class not found" бывает и при полном classpath: в 7
  случаях из 7 (аудит 2026-10-15, случаи 2026-10-14) виновато было имя (угаданный пакет, вложенный класс там, где на деле пакет),
  флаг после имени класса (тогда в ошибке стоит сам флаг: `class not found: -constants`) или относительный `-cp` после неудавшегося
  `cd`. Сверь имя: для jar `unzip -l файл.jar | grep Имя`, для папки `find папка -name 'Имя*.class'`; вложенный класс бери в
  одинарные кавычки `'A$B'`; `-cp` давай абсолютным путём. Если `unzip -l` класса в jar мода не показывает, он может лежать
  во вложенном jar `META-INF/jarjar/*.jar` (так у Sable 2.0.6 и Create Aeronautics bundled 1.3.2; причина 3 из 17 "class not
  found" 2026-10-16..22): распакуй вложенный jar во временную папку (`-d`) и добавь его в `-cp` (проверено 2026-10-23).

## Границы
- Файлы .bat/.cmd и вложенный в них PowerShell: `windows-shell-dev`. Инструмент PowerShell (Windows PowerShell 5.1) имеет
  свой синтаксис (`&&` в Windows PowerShell 5.1 даёт ошибку разбора, проверено 2026-10-15). `2>&1` у нативной команды делает
  каждую строку её stderr ошибкой NativeCommandError (красный текст с `At line:1`) и при успехе, например `Note: ... deprecated
  API` от javac, а если это последняя команда, код выхода 1: 5 сборок gradlew.bat через `powershell -Command` из Bash
  2026-10-20..21 вернули 1 при BUILD SUCCESSFUL. Суди по BUILD SUCCESSFUL/FAILED и `$LASTEXITCODE`. Запись файлов в
  инструменте: `Set-Content -Encoding utf8`, `Out-File` и `>` пишут UTF-8 с BOM и CRLF в конце (проверено 2026-10-23,
  PowerShell 5.1.26100: инструмент сам задаёт кодировку Out-File, а в простом powershell.exe `>` пишет UTF-16), так .java
  проекта получил BOM. Исходники и конфиги правь через Edit/Write, хотя описание инструмента советует `-Encoding utf8`.
  Ловушки про Git Bash (1, 2, 4 и счёт CR в 6) к нему не относятся, про Python и Java (3, 7-9 и запись CRLF в 6) остаются,
  11, 12 и запись файлов - про него самого (11 ещё и про Java).
- Если в проекте есть своя обёртка (например javap с готовым classpath), используй её, а не `classpath_jar.py`.
- Состояние проекта (версии модов, пути инструкций, статус работ) сюда не писать: это дневник проекта.
- Скрипты (у всех есть `--help`, только stdlib, вывод ASCII): `env_probe.py [папка]` (несуществующая папка даёт WARN, код всегда 0),
  `eol.py файлы` (MIXED или нечитаемый файл дают код 1), `classpath_jar.py out.jar вход... [--skip-missing]` (нет файла из списка,
  `@файла` или папки для out.jar: ошибка с кодом 1).
