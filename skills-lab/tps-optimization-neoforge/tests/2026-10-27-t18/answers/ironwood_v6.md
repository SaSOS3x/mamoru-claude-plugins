**Что ответить коллеге**

Выключать плодородие рано. Его вывод опирается на один прогон, а профиль не объясняет такой выигрыш. Миксин через Connector, скорее всего, встанет. Реестр масок, судя по профилю, даёт больше, чем почва.

1. **Цифры коллеги.**
   - База: 6:35, 6:52, 6:20, среднее 6:35 (395 с), разброс около 30 с (примерно 8% от среднего).
   - 5:10 (310 с) - это -85 с, около -21%. Это больше разброса, но прогон один, и перед нами две разные оценки.
   - `SoilSystem.tick` занимает 3,1% потока сервера. Этот поток 61% времени простаивает в `waitUntilNextTick`.
   - Скорость Chunky в таком прогоне задают рабочие потоки C2ME, а не поток сервера. Доля метода в профиле - потолок прибавки для его потока, и убрать 3% простаивающего потока нельзя заметить на фоне разброса.
   - Значит, -21% нельзя целиком приписать `SoilSystem.tick`. Либо это шум, либо `soilTicks=false` изменил больше, чем профилированный метод. Например, синхронные ожидания чанков из `getBlockState` мешают воркерам, или выключение что-то ещё отключает. Это гипотезы, их надо проверять замерами.
   - Пока причина не ясна, "выигрыш от плодородия -20%" нельзя считать установленным.

2. **Реестр масок.**
   - `StructureMaskRegistry.sample` занимает 14,2% собственного времени воркеров C2ME, то есть того потока, который ограничивает прогрузку. Это потолок прибавки по доле: ожидать надо не больше примерно 14% времени воркеров, то есть не более 55 с из 395. Реально меньше, если воркеры иногда ждут не его.
   - Цикл идёт по всем маскам с начала сессии, так что цена растёт вместе с прогоном. Сравнивать нужно прогоны одной длины.
   - Чинится недолго: для точки считать только маски, которые до неё достают. Нужно проверить, что вклад маски ровно 0.0 дальше её радиуса по X и Z. Тогда порядок суммирования сохраняется и рельеф не меняется.
   - Кэш по колонке чанка в `@ModifyExpressionValue` на чтение списка масок работает без блокировок только если `add` заменяет массив копией (copy-on-write). Если реестр дописывает в ArrayList на месте, нужна блокировка или индекс по чанкам.
   - Равенство надо доказать офлайн на реальных классах: случайные маски и точки, сравнение через `Double.doubleToRawLongBits`, плюс заведомо неправильный фильтр, который обязан провалить проверку.

3. **Миксин в Fabric-мод через Connector.** Возражение не подтверждается. В схожем случае (Sengoku 2.1.5, Connector 2.0.0-beta.17) миксины NeoForge-мода встали.
   - Рецепт: `@Mixin(targets = "<класс>")` плюс MixinExtras (`@WrapOperation`, он есть в NeoForge 21.1).
   - В `neoforge.mods.toml` указать id Hearthfire и точную версию 3.2.0.
   - Байткод смотреть в `<game>/.cache/connector/<мод>_mapped_moj_1.21.1.jar`, имена там мохнатые. Если нужны типы самого мода, подключить этот jar через `compileOnly`.
   - Доказательство в игре - строка из обработчика миксина в `latest.log`. Версию Connector в Ironwood надо проверить.

4. **Почва без отключения.**
   - Перед `getBlockState` стоит `isLoaded`. Эта проверка значит "у чанка есть полный билет", а не "чанк готов", поэтому сервер генерирует чанк синхронно. Лечится заменой на `level.getChunkSource().getChunkNow(x >> 4, z >> 4) != null` и пропуском точки, если чанк не готов, через `@WrapOperation`.
   - Ожидаемый выигрыш по профилю - до 3% потока сервера, то есть в пределах шума для времени Chunky. Он нужен ради геймплея и стабильности (например, чтобы сервер не повисал на ожидании чанка), а не ради -20%.

**Что делать первым**

1. Повторить прогон с `soilTicks=false` ещё минимум 2 раза (всего 3). Параллельно сиять профиль этого варианта: без почвы сравнить доли метода в воркерах и в потоке сервера. Абсолютные числа профиля брать нельзя, он замедляет JVM; нужны только доли. Это быстро и ничего не стоит по коду.
2. Прочитать байткод `StructureMaskRegistry` (`add`, массив или список, формула вклада), написать миксин, доказать равенство офлайн.
3. Только потом миксин для `isLoaded` в `SoilSystem`.
4. Если окажется, что `soilTicks=false` реально даёт много, найти причину по профилю (что ещё отключается) и чинить её у источника. Как временную меру можно выключать почву только на время предварительной генерации и включить обратно для игры.

**Как проверить**

- Один фактор за прогон, 3 прогона каждого варианта на свежей копии того же мира, без spark, той же длины (16 641 чанк), без других тяжёлых процессов.
- Принимать эффект только если он больше разброса базы (около 30 с). Один прогон лучше потолка - шум, пока не повторится.
- Для реестра: ждём не больше -14% к базе, и `sample` должен уйти из верха профиля воркеров. Для почвы: цепочка `isLoaded` -> `getChunkBlocking` пропадает из профиля потока сервера, время в пределах разброса.
- Для геймплея: те же дерево плодородия и поведение почвы в игре; сравнить результат предварительной генерации (мир тот же) с базой.
