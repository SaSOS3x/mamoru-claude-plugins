DIAGNOSIS

The main problem is NOT Distant Horizons and NOT the pauseIfMovingQuickly setting. The server thread waits for chunks, and the world cannot generate chunks as fast as you fly. DH has nothing to show because the server is stalled and generation is behind.

Why "median 6 ms" does not contradict "Can't keep up": MSPT measures only the tick body. When the main thread blocks in getChunkBlocking -> managedBlock (and tasks run in waitUntilNextTick), MSPT stays low while the server falls behind wall-clock time. Also, the "25000ms or 500 ticks" number is a backlog accumulated since the last warning (printed at most once per ~300 ticks of schedule), not a rate. Under sustained overload, real MSPT is about 50 + N/300 ms, so with N=25000 that is about 133 ms, i.e. about 7.5 TPS. Compute real TPS from the warning timestamps (wall time between two warnings divided by 300 ticks), not from /spark tps MSPT.

Causes in order of impact

1. The chunk wait under the player (72% of the server thread in Profile 1). The chain handleMovePlayer -> doCheckFallDamage -> getFluidState -> getChunkBlocking is vanilla: at 30 blocks/s the player moves faster than chunks generate, and the server waits for the chunk under him. A mod config on the client cannot fix this. The levers are pre-generation and faster generation. That is why your pre-generated world is fine. It also explains the DH holes: DH's LOD builder needs generated chunks, and the server is stalled. This is consistent with the observation that switching pauseIfMovingQuickly off changes nothing.
   Caveat: the profile is from the Java sampler, which itself drops TPS (to about 1 here). The shares point at the cause, but the absolute numbers (TPS about 1) must not be quoted as the real state.

2. Frontier SnowDriftSystem.tick (9% of the server thread) - a mod bug, and a ceiling of at most about 9% gain. isLoaded(pos) only means "the chunk has a FULL ticket", not "the chunk is ready". Calling getBlockState after it makes the server generate the chunk synchronously. 8 spots within 12 blocks of the player every 10 ticks is exactly where new, ungenerated chunks are. It contributes to the stall and adds sync chunk loads, but removing it will not turn the flight into a smooth one: the player's own chunk wait (1) remains. Expect a gain within the spread of the baseline, not a miracle.
   Fix (code/mixin): replace the isLoaded + getBlockState pair with the non-blocking check
   `ChunkAccess c = level.getChunkSource().getChunkNow(pos.getX() >> 4, pos.getZ() >> 4); if (c == null) continue;` and then read `c.getBlockState(pos)` from that chunk (not level.getBlockState, which goes through getChunk again). Skip the spot when the chunk is not ready. If you cannot edit the mod, a mixin with @WrapOperation on that isLoaded (return getChunkNow(...) != null) and on getBlockState does the same. Also check whether it is truly every 10 ticks per player: throttling is fine here, the problem is only the blocking read.

3. CraterRegistry.contribution (15% of C2ME worker self time) - affects pregeneration speed (Chunky), and therefore indirectly the generation speed in flight. It is a global registry walked for every noise sample, growing as structure pieces are added, including at every load from disk, and cleared only at server start - so Chunky slows down the longer the world is played. No config exists; it is a mod fix. Its ceiling is about 15% of the worker time, and only while the workers are the limiting thread.
   Fix: do not walk all craters for every sample. Craters add 0 outside their radius, so keep only those that can reach the sample's chunk column: index by chunk in add() (each chunk key -> list of craters that reach it, in registry order, so the floating-point sum stays identical), or per thread cache an array filtered for the current column (rebuild when column or registry changes). Thread safety: add() must be copy-on-write (replace a volatile array with a longer copy) or take a lock; an in-place append would let a reader miss a crater. Also make add() skip duplicates (same position/ID) when the piece is loaded from disk, otherwise the registry grows with every load. Prove equality offline before trusting it: real classes, random craters and points, compare Double.doubleToRawLongBits of old and new sum, and verify that a deliberately wrong filter fails.

WHAT TO DO FIRST (in order)
- Pre-generate with Chunky around the area you fly (radius larger than the flight corridor); this is the real fix for the symptom. Do it first because it is config/tool only, no code.
- Then fix CraterRegistry (makes pregeneration and in-flight generation faster, grows with world age).
- Then SnowDriftSystem (small, easy, but low ceiling).
- Reduce nothing else in DH: leave pauseIfMovingQuickly as you like; it is not the cause. Do not expect DH to fill holes until chunks exist.

HOW TO MEASURE HONESTLY
- Same load and same world each time: copy a fresh world per run (a new world generates chunks and LODs in the background for minutes and is not comparable to a played one), same flight path, same speed, nothing else heavy running. Keep the profiler OFF in the runs whose numbers you compare.
- Trust: real TPS from wall time (ticks per second between log timestamps / count of "Can't keep up" per minute of flight), time to first chunk/LOD hole size at a fixed distance ahead (for example percentage of the LOD ring ahead that is empty), Chunky chunks/s for runs of the same length (the registry cost grows with the run, so compare equal lengths). One variable per run.
- Do not trust: spark's MSPT median/95th for this problem (they miss the waits); absolute TPS from a profile run (the sampler drops it to about 1); a single run. Take the baseline at least 3 times; one run cannot show an effect smaller than the baseline spread, and a run that beats the ceiling (9% for SnowDrift) is noise until repeated or until the profile of that variant also shows the chain gone.
- Use profiles only for shares: after each fix check that the frame disappeared (SnowDriftSystem chain under getChunkBlocking, CraterRegistry.contribution in the c2me workers), then judge gain from the clean runs. Expected order of gain is bounded by the shares: at most about 9% for SnowDrift, about 15% of worker time for Crater; do not expect more. Quote these shares as ceilings of this profile, not as rates for other packs.
- A hang that does not occur in every run is shown gone only by several clean runs.
