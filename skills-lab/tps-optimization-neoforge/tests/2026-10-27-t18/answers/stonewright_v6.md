**Причина.** `TerraceRegistry.sample` для каждой точки шума обходит все `TerraceArea`, которые когда-либо добавлены. Реестр растёт с каждым куском деревни (и при генерации, и при загрузке из NBT), поэтому чанки/с падают. Каждый `weight` возвращает ровно `0.0`, если `dx >= falloff` или `dz >= falloff`. Значит, для точки в данном чанке почти все коробки ничего не добавляют.

**Коллега неправ.** Миксин сюда влезает. Типы мода берутся из переделанного Connector-jar: `compileOnly files("<game>/.cache/connector/stonewright-3.0.2_mapped_moj_1.21.1.jar")`. В `neoforge.mods.toml` ставим зависимость от `stonewright` ровно `[3.0.2]`: миксин написан под этот байткод. Рефлексия не нужна, поля `public final`. Миксины NeoForge-мода применяются к моду Connector (это проверено на другом моде 2.1.5).

**Правка.** Цикл и `weight()` не трогаем. Подменяем только массив, который читает цикл. Ниже весь код, как просит проект.

```java
@Mixin(targets = "com.stonewright.gen.TerraceRegistry", remap = false)
public abstract class TerraceRegistryMixin {
  @ModifyExpressionValue(method = "sample", remap = false, at = @At(value = "FIELD",
    opcode = Opcodes.GETSTATIC,
    target = "Lcom/stonewright/gen/TerraceRegistry;AREAS:[Lcom/stonewright/gen/TerraceArea;"))
  private static TerraceArea[] sjw$near(TerraceArea[] all, int x, int y, int z) {
    return NearCache.get(all, x, z);
  }
}
final class NearCache {
  private static final class Win { TerraceArea[] src, out; int cx, cz; }
  private static final ThreadLocal<Win> W = ThreadLocal.withInitial(Win::new);
  static TerraceArea[] get(TerraceArea[] all, int x, int z) {
    Win w = W.get(); int cx = x >> 4, cz = z >> 4;
    if (w.src == all && Math.abs(cx - w.cx) <= 1 && Math.abs(cz - w.cz) <= 1) return w.out;
    int x0 = (cx - 1) << 4, x1 = ((cx + 2) << 4) - 1, z0 = (cz - 1) << 4, z1 = ((cz + 2) << 4) - 1;
    ArrayList<TerraceArea> l = new ArrayList<>();
    for (TerraceArea a : all)   // порядок реестра сохраняется
      if (x1 > a.minX - a.falloff && x0 < a.maxX + a.falloff
       && z1 > a.minZ - a.falloff && z0 < a.maxZ + a.falloff) l.add(a);
    w.src = all; w.cx = cx; w.cz = cz; w.out = l.toArray(new TerraceArea[0]);
    return w.out;
  }
}
```

**Почему результат тот же до бита.**
- Окно 3x3 чанка берёт с запасом всё, что может дотянуться до любой точки окна.
- Пропущенные коробки дали бы `+0.0`. Сумма `s` начинается с `+0.0` и неотрицательна, поэтому `s + 0.0` не меняет `s`.
- Порядок слагаемых тот же.
- Ключ кэша берётся из координат самой точки, а не из текущего чанка. Точки за пределами чанка (аквифер, оценка поверхности) просто перестраивают окно: ответ верен всегда.
- Реестр копируется при записи, поэтому проверка `w.src == all` по ссылке ловит и `add`, и `clear`.
- Нужно убедиться по байткоду, что `add` всегда создаёт новый массив, а не пишет в старый.
- Потокобезопасность обеспечена через `ThreadLocal`.
- Перестройка окна стоит O(N), а точек на чанк порядка тысяч, так что это дёшево. Если реестр вырастет до десятков тысяч, индексируем коробки по чанкам в `add`.

**Доказательство, что рельеф не изменился.**
1. Офлайн: настоящие `TerraceArea` и `TerraceRegistry` из jar, случайные коробки, точки по сетке шума. Сюда входят края окна, точки с `dx` равным `falloff-1`, `falloff` и `falloff+1`, и точки вне окна (перестройка). Сравнивать `Double.doubleToRawLongBits(sample)` до и после.
2. Контроль: фильтр, намеренно сломанный на блок (исключать при `dx >= falloff-1`), должен упасть на этом же тесте. Если не упал, тест слишком слаб.
3. В игре: Chunky на небольшой области свежей копии мира, с миксином и без, потом сравнить данные секций чанков (не файлы `.mca`: там метки времени). Сначала дважды прогнать базу без миксина. Порядок появления коробок зависит от гонок C2ME, и мод может сам давать разброс. Если база с базой расходится, сравнение с миксином этим разбросом и ограничено, а главным доказательством остаётся пункт 1.

**Выигрыш.**
- Потолок для рабочих потоков в окне 4-5 минут: 18,1% self-времени. Это примерно 1/(1-0,181) = 1,22 раза или минус 18% времени потока в этом окне.
- За весь прогон выигрыш не равен этому числу. Ранние минуты дешевле, поздние дороже.
- Падение 55 -> 30 чанков/с (-45%) больше, чем объясняют 18%. Либо в конце доля `sample` выше, либо есть другие причины (I/O, GC, другие реестры).
- Моя оценка, как гипотеза: минус 10-20% общего времени (50-100 с из 512), и кривая чанков/с должна стать заметно площе. Это не обещание.
- В остатке: цикл по немногим близким коробкам и сканы при перестройке окна.

**Как измерить честно.**
- Одна и та же свежая копия мира и одна длина прогона (реестр растёт, поэтому короткий прогон занижает выигрыш).
- Базу измерять 3 и более раз (у вас 512, 509, 515: разброс около 3 с). Затем 3 и более прогонов с миксином, по очереди с базой, при выключенных сборках и других тяжёлых процессах.
- Время считать без spark: Java-сэмплер сам замедляет JVM. Брать общее время и чанки/с по минутам из лога Chunky.
- Отдельным прогоном со spark проверить, что `TerraceRegistry.sample` ушёл из верха профиля. Снять и окно 4-5 минут, и позднее окно.
- Если выигрыш сильно меньше потолка, профилировать такой вариант отдельно: значит, тормозит что-то ещё.
- Миксин должен подтвердиться строкой из обработчика в `latest.log` (одна запись при первом вызове).
